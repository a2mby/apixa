## How to read the audit

This is a **static audit** of `main` at `03fde16`: graphify navigation plus direct source reads.
It ran **no** new tests, probes or measurements, and it claims no fresh `pnpm verify`. Therefore:

- Every finding has a **class**: **C** confirmed by direct code reading (behavior is evident in the
  source; still needs a regression test in Batch 0), **P** plausible, needs a reproduction probe,
  **L** known/documented limitation, **S** speculative risk (no evidence of a defect), **N** checked
  and not an issue.
- **Severity is provisional** until Batch 0 reproduces the finding. P0/P1 are never fixed without a
  failing test first. No finding is promoted to "defect" on reading alone if its impact depends on
  a runtime behavior (e.g. fetch redirect handling) that a probe can settle cheaply.
- Not yet read in this audit, so **no verdict** is given: `request/pipeline.ts` outside the cited
  ranges, `request/retry.ts`, `validation/rules.ts`/`collect.ts`, `http/multipart.ts` filename
  handling, `packages/mocking`, and the React controllers beyond the v1.6.0 evidence. Batch 0 completes them.

## Regression test strategy

- **Red first** for every confirmed P0/P1: the failing test is committed in the same batch before the fix.
- **Deterministic fault injection** (`tests/helpers/fault-injection.ts`): a fake `Transport` and a
  scripted backend that can fail, drop a response, delay or expire at a named stage; an injectable
  `saveCheckpoint`; a storage whose commit stages can throw. Stages: before/after each protocol
  step (initiate, part, inspect, renew, complete, abort), before/after persistence, before/after
  mock stage commit, during stream read, during teardown.
- **Race tests** use controlled promises and fake timers, never sleeps or wall-clock races.
- **Real boundaries**: loopback HTTP servers for redirect, size-limit, slow-socket and streaming
  behavior (the v1.4.0/v1.7.0 pattern), and the existing Chromium HTTPS origins for credential isolation.
- **Matrix tests** (errors, mock/live, runtimes) are table-driven so a new case is one row.
- Existing suites are not weakened; any justified edit is recorded with its reason.

## Performance and memory verification

- **Method**: a small shared helper reads `process.memoryUsage()` (with `--expose-gc` where
  available) and counts calls to instrumented Blob/stream/`arrayBuffer` seams; no profiler, no new
  framework. Extends `scripts/measure-mock-memory.mjs` conventions. Measurements are recorded in
  `acceptance-criteria.md`.
- **Realistic sizes**: 64 KiB, 8 MiB (default part), 256 MiB (Node only), 1 GiB source via a lazy
  synthetic `Blob` that never materializes, 10,000 parts, 5,000 mock files.
- **Thresholds (set from Batch 0 baselines, then enforced)**:
  - Peak retained binary memory for an advanced upload ≤ concurrency × chunkSize + one hash chunk
    - a fixed overhead, and **does not grow when the file size doubles** at fixed chunk/concurrency.
  - CPU/allocations per part acknowledgment stay O(1) in part count; a 10,000-part transfer completes
    within a recorded multiple of a 100-part transfer's per-part cost.

### Managed mock-write fault injection (`tests/core/mock-write-faults.test.ts`, 15 tests)

Stages exercised: before any file exists (handler throws), after a file was allocated and before references persist
(response validation fails), caller abort after the handler finished, mock reset between allocation and commit, file
read failure (creation itself), id collision, failed replacement, aborted replacement then successful retry, array
replacement, shared-file deletion, failed/repeated delete, manual files vs cleanup, concurrent writes with one failure,
interleaved replacements of a shared file, and recovery. A reference-integrity invariant (every held ref is stored; every
managed file is referenced) is asserted after each. **Result: no defect** — records and files are unchanged by any failure,
shared files are never freed while owned, manual files are never collected, and the next write succeeds from a consistent
state. `store.adopt` can only fail on a generation mismatch that `runManagedMock` has just checked synchronously, so the
commit-then-adopt window cannot be interleaved. Side effects a custom handler performs outside the mock store are
outside the guarantee, as documented.
